## 什么是线程?

为了**并发执行**`任务`（**程序**），现代操作系统才引进 `进程` 的概念

**引入进程**的目的：更好的使多道批处理程序**并发执行**，提高资源利用率和系统吞吐量。

**引入线程**的目录：减少进程在并发执行时所付出的时空开销，提高操作系统的并发性能。

**线程最直接的理解就是轻量级进程**

 同一个进程地址空间（**同一个进程内部**）中进行任务的并发：**线程/轻量级进程**

线程是一个比进程更小的**活动单位**。它是进程中的**执行路径**（执行分支），线程也是并发的一种形式。 进程内部的所有的线程**共享整个进程的地址空间**。是操作系统能够进行**调度和分派**的最小单位。

有了线程的概念后，

- **资源分配的单位还是进程**。

- 系统的**调度单位**就从 进程变成**线程**

## 详细回答

C++11的**多线程编程**体系包含以下几个核心组件：

线程管理：**std::thread类用于创建和管理线程**，支持可调用对象、函数指针、lambda表达式等多种线程入口点。

**互斥锁机制**：

std::mutex：基本互斥锁

std::recursive_mutex：可重入互斥锁

std::timed_mutex：带超时功能的互斥锁

std::recursive_timed_mutex：可重入带超时互斥锁

**RAII锁管理：**

std::lock_guard：**简单的作用域锁**

std::unique_lock：**更灵活的锁管理，支持延迟锁定、条件变量**等

**条件变量**：std::condition_variable用于**线程间通信**，实现等待-通知机制。

**原子操作**：std::atomic提供**无锁编程支持，适用于简单的数据同步**。

## 代码示例

```c++
#include <iostream>
#include <thread>
#include <mutex>
#include <vector>

std::mutex g_mutex;
int g_counter = 0;

void increment() {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> lock(g_mutex);
        ++g_counter;
    }
}

int main() {
    std::vector<std::thread> threads;

    for (int i = 0; i < 10; ++i) {
        threads.emplace_back(increment);
    }

    for (auto& t : threads) {
        t.join();
    }

    std::cout << "Final counter: " << g_counter << std::endl;
    return 0;
}
```



# 多线程编程

# 1. 线程库的基本使用

## 创建线程

要创建线程，我们需要一个可调用的函数或函数对象，作为线程的入口点。在C++11中，我们可以使用函数指针、函数对象或lambda表达式来实现。创建线程的基本语法如下：

```
#include <thread>std::thread t(function_name, args...);
```

- `function_name` 是线程入口点的函数或可调用对象
- `args...` 是传递给函数的参数

创建线程后，我们可以使用 `t.join()` 等待线程完成，或者使用 `t.detach()` 分离线程，让它在后台运行。

```c++
#include <iostream>
#include <thread>

void printHelloWorld() {
	std::cout << "hello world!" << std::endl;
}

int main() {

	//1. 创建线程
	std::thread thread1(printHelloWorld);
	//thread1.join();
	return 0;
}
```

单纯在主程序中创建一个线程，而不使用`join()`，此时执行时可能会报错，因为如果是单线程的情况下，程序是从上往下走的，当启动线程时， 函数在一边运行，而主程序main不会等这个 `printHellWorld`函数 运行完才执行 `return`，而是直接进行后续操作。

可能当`printHellWorld`函数运行到一半时，主程序已经结束了，这个时候就会报错

- **让主函数等待线程执行完毕---》join()**

当运行到join时,主程序不会立即结束，而是会检查这个线程有没有执行完成。

`join()`函数本身是阻塞的,直到等待的线程执行完毕才会进行后续操作

## **给线程传递参数**：

我们可以使用多种方式向线程传递参数，例如使用函数参数、全局变量、引用等。如：

```
#include <iostream>
#include <thread>
#include <string>

void printHelloWorld(std::string msg) {
	std::cout << msg << std::endl;
}

void increment(int& x) {
	++x;
}

int main() {

	//1. 创建线程
	std::thread thread1(printHelloWorld,"Hello Thread");
	thread1.join();

	int x = 0;
	//使用 std::ref 显式传递引用
	std::thread thread2(increment, std::ref(x));
	thread2.join();
	std::cout << x << std::endl;

	return 0;
}

//输出:
//Hello Thread
//1
```

需要注意的是，当我们使用引用传递参数时，我们需要使用 `std::ref` 来包装引用，否则编译器会报错。==见后文`std::ref()`--传递引用类型==

## 等待线程完成：join()

当我们创建一个线程后，我们可能需要等待它完成，以便获取线程的执行结果或执行清理操作。我们可以使用 `.join()` 方法来等待线程完成。例如，下面的代码创建了两个线程，等待它们完成后输出一条消息：

```c++
#include <iostream>
#include <thread>

void print_message(const std::string& message) {
    std::cout << message << std::endl;
}

int main() {
    std::thread t1(print_message, "Thread 1");
    std::thread t2(print_message, "Thread 2");
    t1.join();
    t2.join();
    std::cout << "All threads joined" << std::endl;
    return 0;
}
//运行结果可能为:
//Thread 2Thread 1
//
//All threads joined
//或:
//Thread 1
//Thread 2
//All threads joined
//或等等...
```

## 线程分离：detach()

**作用**：将子线程与 `std::thread` 对象分离，让子线程在后台独立运行。分离后：
- 子线程不再受 `std::thread` 对象控制。
- 不能再对其调用 `join()`。
- 子线程的状态变为 **detached**。

**关键限制（重点）**：
`detach()` **不能让子线程脱离进程存活**。`main()` 函数返回时，整个进程结束，操作系统会强制终止该进程下的所有线程（无论是否 detach）。

**安全使用场景**：
通常用于**长期运行的后台任务**（如服务器中的日志刷新线程），且主线程本身通过循环、阻塞等待等方式保持进程不退出。

**正确演示代码**：
```cpp
#include <iostream>
#include <thread>
#include <chrono>

void backgroundTask(int id) {
    for (int i = 0; i < 5; ++i) {
        std::cout << "Thread " << id << " running...\n";
        std::this_thread::sleep_for(std::chrono::milliseconds(100));
    }
    std::cout << "Thread " << id << " finished.\n";
}

int main() {
    std::thread t(backgroundTask, 1);
    t.detach();  // 分离线程

    // 必须暂停主线程，防止进程立即退出导致子线程被杀
    std::cout << "Main thread sleeping, process alive...\n";
    std::this_thread::sleep_for(std::chrono::seconds(1));
    std::cout << "Main thread exits, process will terminate now.\n";
    
    // return 0 会结束进程，子线程随之消亡
    return 0;
}
```

```c++
//运行结果为:
主线程处于睡眠状态，进程仍处于运行状态……
Thread 1 running...
Thread 1 running...
Thread 1 running...
Thread 1 running...
Thread 1 running...
Thread 1 finished.
主线程已退出，程序现在将终止。.
```

## joinable()

- 返回一个`bool`值，来判断这个线程是不是可以调用`join`或者`detach`
  - 如果线程可以被 join()或 detach()，则返回true，否则返回 false。
- 如果我们试图对一个不可加入的线程调用 join()或 detach()，则会抛出一个 std::system_error异常。

```c++
#include <iostream>
#include <thread>
#include <string>

void printHelloWorld(std::string msg) {
	std::cout << msg << std::endl;
}

int main() {

	//1. 创建线程
	std::thread thread1(printHelloWorld,"Hello Thread");
	//thread1.join();
	//thread1.detach();
	bool isJoin = thread1.joinable();

	if (isJoin)
	{
		thread1.join();
	}
	return 0;
}
```

## 常见错误:

在使用C++11线程库时，有一些常见的错误需要注意。例如：

- **忘记等待线程完成或分离线程**：如果我们创建了一个线程，但没有等待它完成或分离它，那么在主线程结束时，可能会导致未定义行为。
- **访问共享数据时没有同步**：如果我们在多个线程中访问共享数据，但没有使用同步机制，那么可能会导致数据竞争、死锁等问题。
- **异常传递问题**：如果在线程中发生了异常，但没有处理它，那么可能会导致程序崩溃。因此，我们应该在线程中使用 `try-catch` 块来捕获异常，并在适当的地方处理它。

## 总结

C++11提供了一个强大的线程库，即std::thread。它可以在C++程序中创建和管理线程，提供了一种更加现代化的方式来处理多线程编程。在本文中，我们介绍了std::thread库的基本使用，包括如何创建、启动和管理线程，以及如何等待线程完成和分离线程。同时，我们也提到了一些常见的错误，需要注意避免。

# 2. 线程函数中的数据未定义错误

**C++11 线程函数中的数据传递与生命周期安全**

## 一、核心原则

## 1. `std::thread` 的传参机制

- **默认行为**：`std::thread` 构造函数会**按值拷贝**所有参数，存入线程内部存储。
- **引用失效**：即使线程入口函数声明为引用（如 `void foo(int& x)`），实际传入的也是**拷贝后的临时对象的引用**。
- **强制引用传递**：必须使用 `std::ref` 或 `std::cref` 包装参数，才能将**真正的引用**传递给线程函数。

## 2. 生命周期安全的核心矛盾

| 场景            | 安全前提                                                     |
| :-------------- | :----------------------------------------------------------- |
| 使用 `join()`   | 被引用对象**在线程执行期间存活**（不一定与 `join()` 同作用域） |
| 使用 `detach()` | 被引用对象**必须比线程活得更久**（通常通过堆分配或智能指针转移所有权） |

## 3. 黄金法则

> **谁持有数据，谁就要对数据的生命周期负责。**
> 线程只能安全访问那些**在整个执行期间确定存活**的数据。

## 二、典型案例与修正

### 案例1：传递临时变量（右值）——编译错误

**错误代码**：

```cpp
#include <thread>

void foo(int& x) {
    x += 1;
}

int main() {
    std::thread t(foo, 1);  // ❌ 编译失败
    t.join();
    return 0;
}
```

**问题分析**：

- `std::thread` 内部将字面量 `1` 拷贝为临时 `int` 对象，然后尝试传递给 `foo(int&)`。
- **非常量左值引用不能绑定到右值**，导致编译错误，并非运行时未定义行为。

**正确写法**：

```cpp
// 方案1：改用值传递（子线程操作副本）
void foo(int x) { x += 1; }
std::thread t(foo, 1);

// 方案2：传递左值并使用 std::ref 保持引用语义
int x = 1;
std::thread t(foo, std::ref(x));
```

### 案例2：传递局部变量指针/引用（join 安全，detach 危险）

#### ✅ 安全版本：使用 `join()` 且变量生命周期覆盖线程执行期

```c++
#include <iostream>
#include <thread>

void foo(int* ptr) {
    std::cout << *ptr << std::endl;
}

int main() {
    int x = 1;
    std::thread t(foo, &x);
    t.join();  // 等待线程执行完毕，x 在此期间一直存活 → 安全
    return 0;
}
```

#### ❌ 危险版本：`detach()` 导致悬空引用

```c++
int main() {
    int x = 1;
    std::thread t(foo, &x);
    t.detach();  // 主线程不再等待，可能立即退出 → x 销毁 → 悬空指针
    return 0;
}
```

#### ❌ 隐蔽错误：`join()` 与变量作用域不匹配

```c++
std::thread global_t;

void create_thread() {
    int local = 42;
    global_t = std::thread([](int& val) { val++; }, std::ref(local));
}   // local 在此销毁，但 global_t 仍持有其引用

int main() {
    create_thread();
    global_t.join();  // 线程访问已销毁的 local → 未定义行为
    return 0;
}
```

**修正**：使用 `shared_ptr` 转移所有权（见案例4）。

### 案例3：传递已释放内存的指针

**错误代码**：

```c++
int* ptr = new int(1);
std::thread t(foo, ptr);  // 传递指针
delete ptr;               // 立即释放，子线程可能尚未执行
t.join();                 // 悬空指针访问 → 未定义行为
```

**正确顺序**：

```c++
int* ptr = new int(1);
std::thread t(foo, ptr);
t.join();      // 等待线程完成
delete ptr;    // 安全释放
```

**更优雅的方案**：使用智能指针自动管理。

```cpp
void foo(std::shared_ptr<int> ptr) {
    std::cout << *ptr << std::endl;
}

int main() {
    auto ptr = std::make_shared<int>(1);
    std::thread t(foo, ptr);
    t.join();  // 或 detach()，shared_ptr 确保数据存活
    return 0;
}
```

### 案例4：类成员函数作为线程入口，对象被提前释放

#### ❌ 错误示例

```c++
class MyClass {
public:
    void func() { /* ... */ }
};

int main() {
    MyClass obj;
    std::thread t(&MyClass::func, &obj);
  //            ^^^^^^^^^^^^^^^  ^^^^^
  //            成员函数指针      对象指针（将成为 this）
    //t.detach();    
    return 0;  // ❌ 未 join/detach，std::terminate 终止程序
}
```

问题在于 `obj` 的所有权属于主线程的栈，主线程退出即销毁。**子线程并未获得所有权**，只是借用一个裸指针。

即使加上 `detach()`，`obj` 也会在 `main` 结束时销毁，子线程访问悬空对象。

- 线程要执行的入口函数是 `MyClass` 的成员函数 `func`。
- 调用这个成员函数的对象是 `obj`（即 `&obj` 会作为 `this` 指针传入）。

`std::thread` 内部大致会这样调用：

```c++
// 伪代码，实际通过模板实现
(&obj)->func();
```

也就是说，`std::thread` 构造函数会把第一个参数（成员函数指针）和第二个参数（对象指针）组合成一个可调用对象，然后在新线程中执行 `obj.func()`。

#### 3. 对比：普通函数 vs 成员函数

| 入口函数类型                     | 构造 `std::thread` 的方式              |
| :------------------------------- | :------------------------------------- |
| 普通函数 `void foo(int)`         | `std::thread t(foo, 42);`              |
| 静态成员函数 `static void bar()` | `std::thread t(&MyClass::bar);`        |
| 非静态成员函数 `void func()`     | `std::thread t(&MyClass::func, &obj);` |

#### 4. 为什么 `&` 有时可以省略？

在 C++ 中，获取成员函数指针时 `&` 运算符**不能省略**，但获取普通函数指针时可以省略（函数名会隐式转换为函数指针）。所以写成 `std::thread t(MyClass::func, &obj);` 是**编译错误**，必须写成 `&MyClass::func`。

#### ✅ 正确写法1：使用 `join()` 延长主线程等待

```c++
int main() {
    MyClass obj;
    std::thread t(&MyClass::func, &obj);
    t.join();  // obj 在线程执行期存活
    return 0;
}
```

- `obj` 是**栈上的局部对象**，它的地址是 `&obj`。
- 这里线程的入口函数需要对象指针，所以直接传 `&obj`。
- 因为有 `t.join()` 等待线程结束，`obj` 的生命周期覆盖了整个线程执行期，**无需堆分配或智能指针**。

#### ✅ 正确写法2：`detach()` 场景用 `shared_ptr` 传递对象

```c++

#include <iostream>
#include <thread>
#include <memory>
#include <chrono>

class MyClass {
public:
    void func() {
        std::cout << "Thread " << std::this_thread::get_id() << " started.\n";
        std::this_thread::sleep_for(std::chrono::seconds(1));
        std::cout << "Thread " << std::this_thread::get_id() << " finished.\n";
    }
};

int main() {
    auto obj = std::make_shared<MyClass>();  // 引用计数=1

    std::thread t(&MyClass::func, obj);      // 拷贝传参，引用计数=2
 	// 传值：拷贝 shared_ptr，引用计数 = 2
    // 注意：这里传的是 shared_ptr 对象本身，不是裸指针
    t.detach();                              // 分离线程
    // 主线程即将退出，其 obj 被销毁，引用计数降为 1

    std::cout << "Main thread exits, process still alive until thread finishes.\n";
    // 主线程退出后，进程仍会等待所有非守护线程结束（C++标准未保证，但常见实现会等待detach线程）
    // 主线程结束，但堆上 MyClass 对象仍被子线程持有
    return 0;
}
```

- `std::thread` 构造函数按值传递 `shared_ptr`，触发**拷贝构造**，引用计数+1。
- 主线程的 `shared_ptr` 销毁时，子线程仍持有一份，对象不会释放。
- 子线程执行完后，它内部的 `shared_ptr` 被销毁，引用计数归零，对象自动 `delete`。

此时 `std::thread` 内部会**拷贝** `shared_ptr`，相当于把对象的所有权交给了子线程，所以 `detach()` 也安全。

| 写法                                  | 参数                 | 生命周期管理                 | 适用场景              |
| :------------------------------------ | :------------------- | :--------------------------- | :-------------------- |
| `std::thread t(&MyClass::func, &obj)` | 裸指针               | 依赖调用者保证 `obj` 存活    | 局部对象 + `join()`   |
| `std::thread t(&MyClass::func, obj)`  | `shared_ptr`（按值） | 自动引用计数，线程持有所有权 | `detach()` 或跨作用域 |

### 案例5：私有成员函数作为线程入口

**问题**：私有成员函数无法直接绑定到 `std::thread`。

**解决方案**：

1. **友元函数**包装调用。
2. **公有成员函数**间接调用。

**示例代码**：

```c++
#include <thread>
#include <iostream>

class MyClass {
private:
    void privateFunc(int id) {
        std::cout << "Thread " << id << " in privateFunc\n";
    }

public:
    // 方案1：提供公有包装接口
    void run(int id) {
        privateFunc(id);
    }

    // 方案2：声明友元函数
    friend void friendWrapper(MyClass* obj, int id);
};

void friendWrapper(MyClass* obj, int id) {
    obj->privateFunc(id);
}

int main() {
    MyClass obj;

    // 使用公有成员函数
    std::thread t1(&MyClass::run, &obj, 1);

    // 使用友元函数
    std::thread t2(friendWrapper, &obj, 2);

    t1.join();
    t2.join();
    return 0;
}
```

## 三、`std::ref` 的正确使用场景

`std::ref` 用于**显式要求线程构造函数传递引用而非副本**。必须确保被引用对象的生命周期足够长。

```c++
#include <thread>
#include <functional>
#include <iostream>

void increment(int& x) {
    x++;
}

int main() {
    int counter = 0;
    std::thread t(increment, std::ref(counter));  // 传递真实引用
    t.join();
    std::cout << counter << std::endl;  // 输出 1
    return 0;
}
```

# 3. C++11 互斥量解决多线程数据共享问题

## 数据共享问题分析

**在多个线程中共享数据**时，需要注意线程安全问题。如果多个线程同时访问同一个变量，并且其中至少有一个线程对该变量进行了写操作，那么就会出现**数据竞争**问题。数据竞争可能会导致程序崩溃、产生未定义的结果，或者得到错误的结果。

为了避免数据竞争问题，需要使用**同步机制**来确保多个线程之间对共享数据的访问是安全的。**常见的同步机制包括互斥量、条件变量、原子操作等。**

#### 示例代码（存在数据竞争问题）

```c++
#include <iostream>
#include <thread>

int shared_data = 0;

void func() {
    for (int i = 0; i < 100000; ++i) {
        shared_data++;
    }
}

int main() {
    std::thread t1(func);
    std::thread t2(func);
    t1.join();
    t2.join();
    std::cout << "shared_data = " << shared_data << std::endl;    
    return 0;
}
```

定义了一个名为`shared_data`的全局变量，并在两个线程中对其进行累加操作。在`main`函数中，创建了两个线程，并分别调用了`func`函数。在`func`函数中，对`shared_data`变量进行了累加操作。

由于`shared_data`变量是**全局变量**，因此**在两个线程中共享**。对于这种共享的情况，需要使用互斥量等**同步机制**来确保多个线程之间对共享数据的访问是安全的。如果不使用同步机制，就会出现数据竞争问题，导致得到错误的结果。

## 互斥量概念

​	互斥量（`mutex`）是一种用于实现多线程同步的机制，用于确保多个线程之间对共享资源的访问互斥。互斥量通常用于保护共享数据的访问，以避免多个线程同时访问同一个变量或者数据结构而导致的数据竞争问题。

互斥量提供了两个基本操作：

- `lock()`：当一个线程调用 lock()函数时，如果互斥量当前没有被其他线程占用，则该线程获得该互斥量的所有权，可以对共享资源进行访问。如果互斥量当前已经被其他线程占用，则调用lock()函数的线程会被阻塞，直到该互斥量被释放为止。
- `unlock()`：释放互斥量，使其他线程可以获取。

### 修正代码（使用互斥量避免数据竞争）

```c++
#include <iostream>
#include <thread>
#include <mutex>

int shared_data = 0;
std::mutex mtx;

void func(int n) {
    for (int i = 0; i < 100; ++i) {
        mtx.lock();
        shared_data++; 
        // 锁内只做数据操作，尽量不打印,否则可能出现屏幕显示顺序不一致等问题
        std::cout << "Thread " << n
                  << " increment shared_data to " << shared_data << std::endl;
        mtx.unlock();
    }
    std::cout << "Thread线程 " << n << " 循环结束." << std::endl;
}

int main() {
    std::thread t1(func, 1);
    std::thread t2(func, 2);

    t1.join();
    t2.join();    

    std::cout << "Final shared_data = " << shared_data << std::endl;    
    return 0;
}
```

在上述代码中，

- shared_data变量由多个线程共享。
- 互斥量mtx确保多个线程不会同时修改shared_data，从而避免数据竞争。
- mtx.lock()获取互斥量的所有权，保证当前线程独占访问shared_data。
- mtx.unlock()释放互斥量，使其他线程可以继续访问shared_data。

这样就可以确保多个线程之间对shared_data变量的访问是安全的。

- ## 注意 ！

- 本示例**锁的粒度太粗**（锁的范围过大），包含I/O操作。即：**将慢速 I/O 放在锁内会严重降低并发性能，且容易引起输出混乱。**

### 输出示例:

```bash
Thread 2 increment shared_data to 1
....
Thread 2 increment shared_data to 100
Thread线程 2Thread 1 循环结束.
 increment shared_data to 101
Thread 1 increment shared_data to 102
......
Thread 1 increment shared_data to 200
Thread线程 1 循环结束.
Final shared_data = 200
```

- ### 现象描述

1. **Thread 2 疯狂输出（1 - 100）**：
   输出开头全是 Thread 2 在工作，一口气从 1 累加到了 100。Thread 1 似乎完全没动。
2. **打印乱码（Glitch）**：
   在 Thread 2 加到 100 后，出现了奇怪的粘连：
   `Thread线程 2Thread 1 increment shared_data to 101`
3. **Thread 1 接力（101 - 200）**：
   从 101 开始，全变成了 Thread 1 在工作，直到 200。
4. **最终结果正确**：
   `Final shared_data = 200` 完美无缺。

- ### 原理分析

1. #### 为什么 Thread 2 能连续干 100 次，Thread 1 干瞪眼？

**原因：操作系统调度 + 互斥锁释放后的“抢跑”优势。**

- **锁的作用是互斥，不是交替**。互斥量 `mtx` 只保证**同一时刻只有一个人进房间**，但它**不保证排队顺序**（不是排队叫号）。

- **代码结构决定了连贯性**：

  ```c++
  mtx.unlock();  // 1. 刚释放锁，Thread 2 刚出门
  // 循环回到开头
  mtx.lock();    // 2. 由于 Thread 2 刚执行完，CPU 缓存是热的，它极大概率立刻再次拿到锁
  ```

  这就好比**跑步接力**：虽然把棒子（锁）放在了地上，但放棒子的人（Thread 2）转身最快，又把棒子捡起来了。**Thread 1 根本抢不到 CPU 时间片。**

2. #### 为什么会出现 `Thread线程 2Thread 1 ...` 这种乱码？

**原因：锁的范围太大，包含了 I/O 操作。**

- 你在 `lock()` 和 `unlock()` 之间放了 `std::cout`。
- `std::cout` 输出到屏幕是非常慢的操作。
- **但是**，`std::cout` 内部也有自己的锁（保证单行不打断）。在你的 Thread 2 完成第 100 次循环、**还没执行 `unlock()`** 的一瞬间，发生了调度切换（线程上下文切换）。
- **结果**：Thread 2 的 `std::cout << "Thread线程 " ...` 打出了一半 (`Thread线程 2`)，操作系统切换到 Thread 1，Thread 1 拿到了 `mtx` 锁，开始输出 `Thread 1 increment ...`，于是就粘在了一起。
- 正确结果应该是:

```c++
Thread线程 2 循环结束.
Thread 1  increment shared_data to 101

//Thread线程 2Thread 1 循环结束.
// increment shared_data to 101
```

3. #### 为什么最终数据 `200` 是正确的？

**原因：`shared_data++` 被互斥量保护了。**

- 无论控制台输出的文字乱成什么样，在**内存**中，执行 `shared_data++` 这行代码时，CPU 一定是独占访问该变量的。
- 这说明 `std::mutex` 完成了它的核心使命——**数据完整性保护**。

- ### 结论与启示

| 观察到的现象                 | 说明的道理                                                   | 改进方向（上次对话中提到的优化）                            |
| :--------------------------- | :----------------------------------------------------------- | :---------------------------------------------------------- |
| **Thread 2 连续运行 100 次** | **互斥量保证互斥，不保证公平轮转**。C++ 标准没有规定解锁后必须让给另一个等待的线程。 | 如果需要交替执行，需要**条件变量**，而不是单纯依赖互斥量。  |
| **控制台输出乱序粘连**       | **锁的粒度太粗**。将慢速 I/O 放在锁内会严重降低并发性能，且容易引起输出混乱。 | **锁只保护数据**：把 `std::cout` 移到 `unlock()` **之后**。 |
| **最终结果正确**             | 虽然调度看起来随机，但**临界区代码是原子执行的**，验证了互斥量的有效性。 | 验证了数据安全。                                            |

> **互斥量让你的数据变安全了，但它没让你的打印变好看，也没让两个线程变得彬彬有礼地交替运行。**

| :-------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |

# 4、C++11 互斥量死锁

## 互斥量死锁问题

假设有两个线程 T1 和 T2，它们需要对两个互斥量mtx1和mtx2进行访问，而且需要按照以下顺序获取互斥量的所有权：

> - **T1**先获取 mtx1的所有权，再获取mtx2的所有权。
> - **T2**先获取mtx2的所有权，再获取mtx1的所有权。

如果两个线程同时执行，就会出现死锁问题。因为 T1获取了mtx1的所有权，但是无法获取mtx2的所有权，而 T2 获取了mtx2的所有权，但是无法获取mtx1的所有权，两个线程互相等待对方释放互斥量，导致死锁。

## 死锁总结

“死锁是多线程编程中常见的问题。当多个线程持有部分资源并试图获取对方持有的资源时，容易形成循环等待。

**解决方案主要有两种**：

1. **静态顺序法**：编码时强制规定互斥量的全局锁定顺序。
2. **动态避免法**：使用 C++11 标准库提供的 `std::lock` 函数一次性锁定多个互斥量，或使用 C++17 的 `std::scoped_lock`，利用 RAII 机制在编译期/运行期规避死锁风险，同时保证异常安全。”

> 死锁是多线程编程中常见的问题之一。当多个线程以不同的顺序获取多个互斥量的所有权时，就可能发生死锁。为了避免死锁，必须保证所有线程按照相同的顺序获取互斥量的所有权，这样可以有效降低死锁的风险，提高程序的稳定性。

## 解决方案

为了解决这个问题，可以让两个线程按照相同的顺序获取互斥量的所有权。例如：

> - **都先获取** `mtx1`**的所有权，再获取** `mtx2`**的所有权**。
> - 或：
> - **都先获取** `mtx2`**的所有权，再获取** `mtx1`**的所有权**。

## 示例工程代码

```c++
#include <iostream>
#include <thread>
#include <mutex>

std::mutex mtx1, mtx2;

void func(int n) {
    // 正确示范：使用 std::lock 原子性地锁定两个互斥量，防止死锁
    	// 第 1 步：原子地锁定两个互斥量（安全，不会死锁）
    std::lock(mtx1, mtx2);
    
    // 领养锁的所有权，让 RAII 负责解锁（即使抛异常也会自动解）
    	// 第 2 步：将两把锁交给 RAII 对象管理，确保异常时自动解锁
    std::lock_guard<std::mutex> lock1(mtx1, std::adopt_lock);
    std::lock_guard<std::mutex> lock2(mtx2, std::adopt_lock);
    
    std::cout << "Thread " << n << " got both locks safely." << std::endl;
    
    // 临界区操作...
        // 第 3 步：临界区代码
        // ... 操作共享资源 ...
    
} // 函数结束，自动逆序解锁 mtx2, mtx1，完美！
	// 第 4 步：函数结束，lock2 析构 -> mtx2.unlock()
  	//        lock1 析构 -> mtx1.unlock() （逆序解锁）

int main() {
    std::thread t1(func, 1);
    std::thread t2(func, 2);
    t1.join();
    t2.join();
    return 0;
}
```

### 分析:

### 一、`std::lock` —— 原子性锁定多个互斥量

**函数原型**（简化理解）：

```c++
template <typename Mutex1, typename Mutex2>
void lock(Mutex1& m1, Mutex2& m2);
```

**作用**：

- 一次性尝试获取两个（或多个）互斥锁的所有权。
- 保证**要么全部锁成功，要么一个都不锁**。绝不会出现“锁住一个，等另一个”的中间状态。

**内部原理**（防死锁机制）：
它内部使用类似 **“尝试-回退”** 的算法。例如先锁 `m1`，再尝试锁 `m2`；如果 `m2` 已被别人占住，它会**主动释放已经拿到的 `m1`**，然后重试。这样就不会形成两个线程互相拿着对方需要的锁僵持不下的局面。

### 二、`std::lock_guard` 带 `std::adopt_lock` —— 领养已锁资源

**普通 `std::lock_guard`** 的行为是：

```c++
std::lock_guard<std::mutex> guard(mtx);  // 构造时调用 mtx.lock()
// ...
// 析构时调用 mtx.unlock()
```

**带 `std::adopt_lock` 的行为变化**：

```c++
std::lock_guard<std::mutex> guard(mtx, std::adopt_lock);
// 构造时：什么都不做，假定 mtx 已经被当前线程锁住了
// 析构时：调用 mtx.unlock()
```

- `std::adopt_lock` 是一个**空标记类型**，用来告诉 `lock_guard` 的构造函数：“这个锁已经被我锁过了，你**别再去锁一次**，只负责帮我解锁就行。”

### 三、组合写法逐行解析

| 问题                                             | 答案                                                         |
| :----------------------------------------------- | :----------------------------------------------------------- |
| **为什么不用普通 `lock_guard` 直接锁？**         | 若写成 `lock_guard<mutex> g1(mtx1); lock_guard<mutex> g2(mtx2);`，当线程 A 拿了 `mtx1` 等待 `mtx2`，线程 B 拿了 `mtx2` 等待 `mtx1`，**死锁发生**。 |
| **为什么有了 `std::lock` 还要用 `lock_guard`？** | `std::lock` **只负责上锁，不管解锁**。若在临界区抛出异常，程序会带着锁跳出函数，导致**死锁**。`lock_guard` 保证无论正常返回还是异常，析构时**一定解锁**（RAII 原则）。 |
| **为什么要加 `std::adopt_lock`？**               | 因为 `mtx1` 和 `mtx2` 已经被 `std::lock` 锁上了。如果 `lock_guard` 构造时再调用 `mtx1.lock()`，线程会**自己阻塞自己**，永远卡死。`std::adopt_lock` 跳过了构造加锁步骤，只接管解锁职责。 |

### 四、更简洁的 C++17 替代方案

一行代码可以替代上面两步：

```cpp
std::scoped_lock lock(mtx1, mtx2); // 兼具 std::lock 的原子性 + RAII 自动解锁
```

- **优势**：不易遗漏 `std::adopt_lock`，代码更短。
- **现状**：许多教学/考试环境仍以 C++11 为主，所以**理解 `std::lock` + `adopt_lock` 组合是必须的**。

### 五、核心要点笔记

| 要点                       | 说明                                                         |
| :------------------------- | :----------------------------------------------------------- |
| **防死锁顺序法局限**       | 强制统一加锁顺序虽可行，但复杂项目中易出错。`std::lock` 是运行时避免死锁的可靠手段。 |
| **`std::lock` 职责**       | 原子性获取 ≥2 个锁，绝不部分获取。                           |
| **`std::adopt_lock` 职责** | 告诉 RAII 对象：**只解锁，不加锁**。                         |
| **组合原因**               | `std::lock` 解决“怎么安全地锁住多个”；`lock_guard` 解决“怎么保证一定解锁”。两者分工，缺一不可。 |

# 5、C++11 `lock_guard` 与 `std::unique_lock`

`lock	/lɑːk/	v.锁住/n.锁`

`guard	/ɡɑrd/	n.	守卫，看护`

- **`std::lock_guard`**：极简 RAII 锁，构造即锁，析构即解。**除了 RAII 什么额外功能都没有，性能最高。**
- **`std::unique_lock`**：全能 RAII 锁，可延迟锁、可提前解锁、可转移所有权。**唯一的代价是比 `lock_guard` 多一个 `bool` 成员变量，稍重一点点。**

## 使用场景决策树（工程设计核心）

```tex
是否需要配合条件变量 (std::condition_variable) 使用？
    ├── 是 → 必须用 std::unique_lock （条件变量 wait() 只接受 unique_lock）
    └── 否 → 是否需要手动提前解锁、延迟锁定、或尝试锁定？
            ├── 是 → 用 std::unique_lock
            └── 否 → 用 std::lock_guard （简洁、高效、意图明确）
```

## std::lock_guard

`std::lock_guard`是 C++ 标准库中的一种互斥量封装类，用于保护共享数据，防止多个线程同时访问同一资源而导致的数据竞争问题。

- ## 特点

- 当构造函数被调用时，该互斥量会被自动锁定。
- 当析构函数被调用时，该互斥量会被自动解锁。
- `std::lock_guard`对象不能复制或移动，因此它只能在局部作用域中使用。

## std::unique_lock

`std::unique_lock`是 C++ 标准库中提供的一个互斥量封装类，用于在多线程程序中对互斥量进行加锁和解锁操作。它的主要特点是可以对互斥量进行更加灵活的管理，包括延迟加锁、条件变量、超时等。

### 成员函数

- `lock()`：尝试对互斥量进行加锁操作，如果当前互斥量已经被其他线程持有，则当前线程会被阻塞，直到互斥量被成功加锁。
- `try_lock()`：尝试对互斥量进行加锁操作，如果当前互斥量已经被其他线程持有，则函数立即返回false，否则返回true。
- `try_lock_for(const std::chrono::duration<Rep, Period>& rel_time)`：尝试对互斥量进行加锁操作，如果当前互斥量已经被其他线程持有，则当前线程会被阻塞，直到互斥量被成功加锁，或者超过了指定的时间。
- `try_lock_until(const std::chrono::time_point<Clock, Duration>& abs_time)`：尝试对互斥量进行加锁操作，如果当前互斥量已经被其他线程持有，则当前线程会被阻塞，直到互斥量被成功加锁，或者超过了指定的时间点。
- `unlock()`：对互斥量进行解锁操作。

### 构造函数

- `unique_lock() noexcept = default`：默认构造函数，创建一个未关联任何互斥量的std::unique_lock对象。
- `explicit unique_lock(mutex_type& m)`：构造函数，使用给定的互斥量m进行初始化，并对该互斥量进行加锁操作。
- `unique_lock(mutex_type& m, defer_lock_t) noexcept`：构造函数，使用给定的互斥量m进行初始化，但不对该互斥量进行加锁操作。
- `unique_lock(mutex_type& m, try_to_lock_t) noexcept`：构造函数，使用给定的互斥量m进行初始化，并尝试对该互斥量进行加锁操作。如果加锁失败，则创建的std::unique_lock对象不与任何互斥量关联。
- `unique_lock(mutex_type& m, adopt_lock_t) noexcept`：构造函数，使用给定的互斥量m进行初始化，并假设该互斥量已经被当前线程成功加锁。

| 标签               | 作用                                       | 典型使用场景                              |
| :----------------- | :----------------------------------------- | :---------------------------------------- |
| （无标签）         | 构造时立即加锁                             | 最普通的临界区保护                        |
| `std::defer_lock`  | 构造时**不加锁**，关联互斥量               | 配合 `std::lock(m1, m2)` 同时锁多个互斥量 |
| `std::try_to_lock` | 构造时尝试加锁，失败则不持有锁             | 执行可选任务，拿不到锁就去做别的事        |
| `std::adopt_lock`  | 假定互斥量**已被当前线程锁定**，只接管解锁 | 接盘 `std::lock` 的成果，保证异常安全     |

## 为什么条件变量必须用 `unique_lock`？

条件变量的 `wait` 函数内部需要：

1. 原子地释放锁并进入等待状态。
2. 被唤醒后重新获取锁。

`lock_guard` **没有 `unlock()` 和 `lock()` 成员函数**（它只在析构时解锁，构造时加锁），无法完成“临时解锁再重新加锁”的动作。而 `unique_lock` 提供了 `unlock()` 和 `lock()` 成员函数，可以灵活控制。

## 性能与可移植性提示（了解即可）

- `sizeof(std::lock_guard<std::mutex>)` 通常为 4/8 字节（只存一个引用/指针）。
- `sizeof(std::unique_lock<std::mutex>)` 通常为 8/16 字节（多了 `bool owns` 标志）。
- **结论**：能用 `lock_guard` 的地方绝不用 `unique_lock`，这是现代 C++ 的惯用法。

## 示例代码

**示例 1：`lock_guard` 的标准用法（保护简单作用域）**

```cpp

    std::lock_guard<std::mutex> guard(mtx); // 加锁
    ++counter;
    // 出作用域，自动解锁
}
```

**示例 2：`unique_lock` 配合条件变量（它的主场）**

```cpp
void consumer() {
    std::unique_lock<std::mutex> lock(mtx);
    cv.wait(lock, []{ return ready; }); // wait 需要 unique_lock

```

**示例 3：`unique_lock` 实现延迟锁定（解决死锁的标准写法）**

```cpp

    std::unique_lock<std::mutex> lock1(from.mtx, std::defer_lock);
    std::unique_lock<std::mutex> lock2(to.mtx, std::defer_lock);

    // ... 安全转账 ...
}
```

## 总结

> “`std::lock_guard` 和 `std::unique_lock` 都是 RAII 风格的互斥量管理器。`lock_guard` 是轻量级、不可移动的锁守卫，适用于简单的、作用域级别的互斥保护；`std::unique_lock` 则提供了延迟锁定、尝试锁定、提前解锁以及所有权转移等高级功能，是配合条件变量、实现复杂同步逻辑的必备工具。在实际开发中，应遵循**最小权限原则**：除非需要额外灵活性，否则优先使用 `std::lock_guard`。”

## 单例模式的线程安全问题

```c++
class Singleton {// 现代 C++ 单例唯一真神
public:
    static Singleton& getInstance() {
         static Singleton instance;// C++11 保证线程安全初始化
```

自 **C++11 起**，函数内的**静态局部变量初始化是线程安全的**。编译器会自动生成隐式的互斥锁或原子检查代码，保证无论多少线程同时首次调用 `getInstance()`，构造函数 `Singleton()` **有且仅被执行一次**。

- 这个特性被称为 **Magic Statics**（魔法静态）。

| 方案                  | 代码示例                     | 线程安全？         | 推荐度 | 适用场景                                         |
| :-------------------- | :--------------------------- | :----------------- | :----- | :----------------------------------------------- |
| **Meyers' Singleton** | `static Singleton instance;` | **C++11 起安全**   | ⭐⭐⭐⭐⭐  | **首选**，代码最少，性能最高                     |
| `std::call_once`      | 配合指针                     | 安全               | ⭐⭐     | 需要在**堆**上创建对象，或者初始化逻辑极其复杂时 |
| 双重检查锁定 (DCL)    | `if + mutex`                 | 需用 `atomic` 修正 | ⭐      | 除非你穿越回了 C++03，否则**不要用**             |

| 问题                                      | 正确观点（笔记应写）                                         |
| :---------------------------------------- | :----------------------------------------------------------- |
| 静态局部变量是线程安全的吗?(√)            | **C++11 之后是绝对安全的**，这是标准明确规定的。             |
| 必须用 `call_once` 解决单例线程安全吗?(×) | 单例首选 Meyers' Singleton。`call_once` 用于处理**更广义的一次性初始化**（如非局部静态对象、需动态内存的初始化）。 |
| `std::unique_ptr` 是必要的吗?(×)          | Meyers 单例不需要指针，直接返回引用。指针增加了复杂度且略微降低性能。 |

> “在 C++11 及之后的标准中，实现线程安全的单例模式**首选 Meyers' Singleton**（函数内静态局部变量）。编译器会确保初始化过程的线程安全，无需显式加锁。`std::call_once` 与 `std::once_flag` 主要用于**非静态局部变量的场景**，例如需要动态内存分配、初始化顺序控制、或者初始化一个不提供静态访问的库资源。将 `call_once` 用于普通单例模式属于过度工程。”

# 7 、C++11 condition_variable 使用场景

`std::condition_variable` 的使用步骤(**条件变量**)

std::condition_variable是 C++11 中用于线程间通信的同步机制，可以用于实现线程的等待与通知机制。其使用步骤如下：

1. **创建一个 `std::condition_variable` 对象**。
2. **创建一个互斥锁 `std::mutex` 对象**，用于保护共享资源的访问。
3. **在需要等待条件变量的地方**：
   - 使用 `std::unique_lock<std::mutex>` 对象锁定互斥锁。
   - 调用`std::condition_variable::wait()`、`std::condition_variable::wait_for(`)或`std::condition_variable::wait_until()`函数等待条件变量。
4. 在其他线程中需要通知等待的线程时，调用`std::condition_variable::notify_one()`或`std::condition_variable::notify_all()`函数来通知等待的线程。

## 示例:经典生产者与消费者模型

下面是一个简单的生产者-消费者模型的案例，其中使用了`std::condition_variable`来实现线程的等待和通知机制：

```c++
#include <iostream>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <queue>

std::mutex g_mutex;//互斥锁，用于多线程编程中保证数据同步
std::condition_variable g_cv;//条件变量,用于线程同步的变量，通常与互斥锁一起使用
std::queue<int> g_queue;//队列

void Producer() {
    for (int i = 0; i < 10; i++) {
        {            
            std::unique_lock<std::mutex> lock(g_mutex);
            //unique_lock互斥量封装类，用于在多线程程序中对互斥量进行加锁和解锁操作。
            g_queue.push(i);            
            std::cout << "Producer: produced " << i << std::endl;
        }
        g_cv.notify_one();  //通知等待的线程      
        std::this_thread::sleep_for(std::chrono::milliseconds(100));//休眠100毫秒
    }
}

void Consumer() {    
    while (true) {        
        std::unique_lock<std::mutex> lock(g_mutex);
        //unique_lock互斥量封装类，用于在多线程程序中对互斥量进行加锁和解锁操作。
        g_cv.wait(lock, []() { return !g_queue.empty(); });//等待并检查条件变量
        int value = g_queue.front();//返回queue第一个元素的引用
        g_queue.pop();//删除队列第一个元素        
        std::cout << "Consumer: consumed " << value << std::endl;
    }
}

int main() {    
    std::thread producer_thread(Producer);    
    std::thread consumer_thread(Consumer);
    producer_thread.join();
    consumer_thread.join();    
    return 0;
}
```

别担心，这个模型是多线程编程里最经典的**面试必考题**，刚接触确实会觉得绕。我们不谈虚的概念，直接**逐行拆解**代码，用**快递员和取件人**的例子帮你建立直观画面。

### 场景比喻：一个快递柜（共享队列）
- **生产者**：快递员，往柜子里放快递。
- **消费者**：你，从柜子里取快递。
- **柜子 (`g_queue`)**：只能一个人往里放/往外拿（需要锁）。
- **短信通知 (`g_cv`)**：快递员放完快递后给你发短信：“有快递了，来拿吧！”

---

### 代码逐段讲解（请对照代码阅读）

#### 1. 全局变量准备
```cpp
std::mutex g_mutex;                // 门锁，保证柜子一次只被一个人操作
std::condition_variable g_cv;      // 短信通知系统
std::queue<int> g_queue;           // 柜子本身（共享数据）
```

#### 2. 生产者 (Producer) —— 快递员
```cpp
void Producer() {
    for (int i = 0; i < 10; i++) {
        {            
            std::unique_lock<std::mutex> lock(g_mutex); // 【步骤1】锁上柜门
            g_queue.push(i);                            // 【步骤2】把快递塞进柜子
            std::cout << "Producer: produced " << i << std::endl; // 打印记录
        } // 【步骤3】锁在这里自动释放（离开大括号作用域）
        
        g_cv.notify_one();                              // 【步骤4】发短信：“有快递！”
        std::this_thread::sleep_for(std::chrono::milliseconds(100)); // 【步骤5】歇100毫秒
    }
}
```
**每一步解释**：
- **步骤1 (加锁)**：快递员打开柜门前，先确认没人在用柜子。如果有人正在取件，他就**排队等着**。
- **步骤2 (生产)**：把快递放进去。
- **步骤3 (解锁)**：**非常重要**。快递员**关好柜门，离开柜子**。如果他不离开，你就没法靠近柜子取件。
- **步骤4 (发短信)**：发完短信，他就可以去喝口水了。注意短信是在**锁外**发的，因为发短信（通知）不需要占用柜子。
- **步骤5 (休息)**：模拟快递员去取下一件货的时间，让线程慢下来方便观察输出。

#### 3. 消费者 (Consumer) —— 取件人
```cpp
void Consumer() {    
    while (true) {        
        std::unique_lock<std::mutex> lock(g_mutex); // 【步骤A】锁上柜门
        
        // 【步骤B】关键！等待短信 + 检查柜子
        g_cv.wait(lock, []() { return !g_queue.empty(); }); 
        
        int value = g_queue.front();                 // 【步骤C】拿出快递
        g_queue.pop();                               // 【步骤D】扔掉空盒子
        std::cout << "Consumer: consumed " << value << std::endl; // 打印
    }
}
```

**步骤A (加锁)**：你走到柜子前，先把柜门锁上（防止有人在你操作时乱塞东西）。

**步骤B (`g_cv.wait(...)`) —— 最核心、最绕的地方**：
这一行代码实际上做了三件事（原子操作，不可分割）：

1. **检查 Lambda 表达式 `[]() { return !g_queue.empty(); }`**：
   - `!g_queue.empty()` 意思是：“柜子不是空的”。
   - 如果柜子**有快递**，Lambda 返回 `true`，`wait` **直接返回**，什么都不做，继续往下执行。
   - 如果柜子**是空的**，Lambda 返回 `false`，则执行下面的 2 和 3。

2. **释放锁 (`g_mutex.unlock()`) 并且让自己睡觉**：
   - 注意：这是**自动发生**的。`wait` 函数知道你现在拿着锁，它会把锁**先还回去**（让快递员能靠近柜子），然后线程进入**睡眠状态**，不消耗 CPU。

3. **被短信 (`notify_one`) 叫醒后，重新获取锁**：
   - 快递员发了短信后，操作系统把你叫醒。
   - 你醒来的第一件事是**试图重新锁上柜门**（`lock.lock()`）。如果快递员还在放快递，你就得等他放完解锁后才能拿到锁。
   - 拿到锁后，**再次检查 Lambda**（防止你被莫名其妙叫醒，即**虚假唤醒**）。

**步骤C & D (取件)**：确认柜子非空，拿出最前面的快递，把那个位置清空。
**注意**：因为代码里是 `while (true)`，所以取完一件后，循环继续，你会再次去**步骤A**锁门，然后**步骤B**检查。如果柜子又空了，你就又睡着了，等下一次短信。

#### 4. 主函数
```cpp
int main() {    
    std::thread producer_thread(Producer);    
    std::thread consumer_thread(Consumer);
    producer_thread.join();   // 等快递员下班
    consumer_thread.join();   // 这行其实永远不会执行到，因为 Consumer 是死循环
    return 0;
}
```
- `join()` 意思是主线程在这里等着，直到那个线程干完活。
- **注意**：`Consumer` 是个死循环 `while(true)`，所以程序**不会自动结束**，你需要按 `Ctrl+C` 强制关闭。这是教学代码的简化，实际工程中会有退出信号。

### 常见疑问解答（针对你之前的困惑）

**Q1：为什么要把 `g_cv.notify_one()` 放在锁外面？**
- **A**：如果放在锁里面（大括号内），快递员发短信时还**占着柜门**。
- 你一收到短信冲过来，发现柜门锁着，只能**在门口干等**快递员出来。等快递员出来解锁，你才能进去——这白白浪费了一次 CPU 调度。
- 放在锁外面，快递员出来后才发短信，你一到门口门就是开的（或者马上能抢到锁），效率更高。

**Q2：为什么 `Consumer` 里要有那个看起来很奇怪的 `[]() { return !g_queue.empty(); }`？**
- **A**：两个原因。
  1. **防止睡过头**：万一你走到柜子前（步骤A）还没检查，快递员已经把快递放好了并发了短信，然后你才调用 `wait`。如果没有这个检查，你可能会**错过短信**直接睡死过去。有这个检查，你会先看一眼柜子，有货就直接拿了，不睡了。
  2. **防止假短信（虚假唤醒）**：操作系统有时候会抽风，没收到短信也叫醒你。如果没有这个检查，你醒来一看柜子是空的，拿空气，程序就崩了。有这个检查，你醒来发现是空的，会继续倒头睡。

### 总结一句话
**生产者**负责**锁->放货->解锁->通知**。
**消费者**负责**锁->检查->（空则解锁睡觉等通知）->取货->解锁**。

这就像一个带密码锁的快递柜，锁保证了柜子不会乱，短信系统保证了取件人不用一直蹲在柜子前面傻等。

## 说明

使用 std::condition_variable可以实现线程的等待和通知机制，从而在多线程环境中实现同步操作。在生产者-消费者模型中，使用std::condition_variable可以让消费者线程等待生产者线程生产数据后再进行消费，避免了数据丢失或者数据不一致的问题。

> "`std::condition_variable` 是多线程编程中实现**同步等待**的核心工具。它通过 `wait` 机制让线程在条件不满足时进入睡眠，避免 CPU 忙等。
>
> 使用时必须牢记三点：
>
> 第一，必须配合 `std::unique_lock` 使用；
>
> 第二，**必须处理虚假唤醒**，使用带谓词的 `wait` 版本；
>
> 第三，`notify` 通常建议在释放锁之后调用，以减少不必要的上下文切换。掌握条件变量是理解线程间通信、构建生产者-消费者模型的基础。”

#### 1. 条件变量解决的根本问题

互斥量只能解决“互斥访问”，无法解决“按条件等待”。
例如：消费者必须等队列非空才能取数据。如果用纯互斥量轮询（忙等待），CPU 会空转。条件变量让线程**睡眠**，直到条件满足被唤醒，**释放 CPU 资源**。

#### 2. 核心 API 与执行流程（考试重点）

| 操作               | 作用                                                         | 注意事项                                                     |
| :----------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| `wait(lock, pred)` | 1. 若 `pred()` 为 `false`，**原子地**释放锁并阻塞； 2. 被唤醒后**重新获取锁**，再次检查 `pred()`。 | 必须用 `std::unique_lock`。                                  |
| `wait(lock)`       | 不带谓词，唤醒后**不会自动重检条件**，需手动 `while` 循环。  | **极易受虚假唤醒影响，不推荐直接使用**。                     |
| `notify_one()`     | 唤醒**一个**等待线程。                                       | 如果唤醒的线程发现条件不满足（如被其他线程抢先），它会再次睡眠。 |
| `notify_all()`     | 唤醒**所有**等待线程。                                       | 只有一个线程能拿到锁继续执行，其余继续阻塞在锁上。           |

#### 3. 虚假唤醒 (Spurious Wakeup) —— 必背概念

- **定义**：线程在没有收到 `notify` 的情况下，可能从 `wait` 返回。

- **原因**：操作系统调度、信号中断或硬件层面的原因。

- **应对**：**必须使用带谓词的 `wait` 版本，或在 `while` 循环中调用 `wait`**。

- **标准写法对比**：

  ```c++
  // 错误：脆弱，虚假唤醒会导致乱取数据
  if (queue.empty()) cv.wait(lock);
  
  // 正确：循环检查（谓词内部就是 while）
  cv.wait(lock, []{ return !queue.empty(); });
  ```

#### 4. 生产者代码的锁粒度分析（原文中的细节问题）

原文 `Producer` 片段：

```c++
{
    std::unique_lock<std::mutex> lock(g_mutex);
    g_queue.push(i);
    std::cout << ... << std::endl;
}
g_cv.notify_one();
```

- **正确点**：`notify_one` **放在锁外**。如果在锁内通知，被唤醒的消费者会立刻尝试获取仍被生产者持有的锁，导致**惊群效应**后再次阻塞，浪费一次上下文切换。
- **潜在问题**：`std::cout` 也在锁内。IO 操作慢，增大了锁持有时间。实际工程中通常只将**纯内存操作**放入锁内。

#### 5. 消费者退出机制（完善代码）

原文 `Consumer` 无限循环，无法优雅退出。典型做法：

```c++
void Consumer() {
    while (true) {
        std::unique_lock lock(g_mutex);
        g_cv.wait(lock, []{ return !g_queue.empty() || g_done; });
        if (g_done && g_queue.empty()) break;
        // 消费...
    }
}
```

#### 6. 为什么 `std::condition_variable` 必须搭配 `std::unique_lock`？

这是面试高频题。答案：

1. `wait()` 内部需要**临时解锁**（让生产者能拿到锁放入数据）。
2. `wait()` 返回时需要**重新加锁**（保证消费者独占访问队列）。
3. `std::lock_guard` **没有 `unlock()` 和 `lock()` 成员函数**，无法完成上述动作。
4. `std::unique_lock` 提供了灵活的 `lock()` / `unlock()` 控制能力。

## 常见陷阱与正确用法速查表

| 陷阱         | 错误表现                                                     | 正确做法                                                     |
| :----------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| **丢失唤醒** | 消费者还未 `wait`，生产者已 `notify`，唤醒信号丢失，消费者永久阻塞。 | 确保修改条件变量关联的共享数据（如队列）时**持有同一把锁**，并在锁内决定是否 `notify`（或确保 `wait` 先发生）。 |
| **惊群效应** | `notify_all` 后大量线程抢锁，只有一个获胜，其余白唤醒。      | 优先用 `notify_one`，除非条件变化可能让多个线程同时继续。    |
| **死锁**     | 在持有锁的情况下调用 `wait`，但未正确释放锁（如用错锁类型）。 | 用 `std::unique_lock` 而非 `lock_guard`。                    |

# 8 、C++11 跨平台线程池

## 跨平台线程池实现

本实现使用 C++11 标准库中的std::thread、std::mutex、std::condition_variable、std::function和 std::queue等组件来创建一个线程池。

### 线程池实现代码

```c++
#include <iostream>
#include <thread>
#include <mutex>
#include <condition_variable>
#include <functional>
#include <queue>

class ThreadPool {
public:
    ThreadPool(int numThreads) : stop(false) {
        for (int i = 0; i < numThreads; ++i) {
            threads.emplace_back([this] {
                while (true) {
                    std::unique_lock<std::mutex> lock(mutex);
                    // 等待条件：要么被通知停止，要么队列非空
                    condition.wait(lock, [this] { return stop || !tasks.empty(); });
                 // 被唤醒后，检查是否是停止信号且队列已空 -> 线程退出
                   
                    if (stop && tasks.empty()) {
                        return;
                    }
                 // 取出任务（使用移动语义避免拷贝）

                    std::function<void()> task(std::move(tasks.front()));
                    tasks.pop();
                   // 关键：执行任务前必须解锁！
                    lock.unlock();
                    task();// 执行任务（可能耗时很长）
                }
            });
        }
    }

    ~ThreadPool() {
        {
            std::unique_lock<std::mutex> lock(mutex);
            stop = true;// 1. 设置退出标志
        }
        condition.notify_all();// 2. 唤醒所有睡眠线程
        for (std::thread& thread : threads) {
            thread.join();// 3. 等待所有线程执行完毕退出
        }
    }

//enqueue 函数：向线程池提交任务
    template<typename F, typename... Args>
    void enqueue(F&& f, Args&&... args) {
// 将函数和参数绑定为一个 void() 可调用对象
        std::function<void()> task(std::bind(std::forward<F>(f), std::forward<Args>(args)...));
//std::forward<F>(f) 和 std::forward<Args>(args)... 是完美转发，保证参数是左值还是右值原封不动地传进去，避免多余的拷贝或移动。
        {
            std::unique_lock<std::mutex> lock(mutex);
            tasks.emplace(std::move(task));// 移动入队
        }
        condition.notify_one();// 唤醒一个等待线程
    }

private:
    std::vector<std::thread> threads;
    std::queue<std::function<void()>> tasks;
    std::mutex mutex;
    std::condition_variable condition;
    bool stop;
};

int main() {
    ThreadPool pool(4);
    for (int i = 0; i < 8; ++i) {
        pool.enqueue([i] {
            std::cout << "Task " << i << " is running in thread " << std::this_thread::get_id() << std::endl;
            std::this_thread::sleep_for(std::chrono::seconds(1));
            std::cout << "Task " << i << " is done" << std::endl;
        });
    }
    return 0;
}
```

### 说明

在这个示例中，我们定义了一个 ThreadPool类，并在构造函数中创建了指定数目的线程。在每个线程中，线程会不断地从任务队列中获取任务并执行，直到线程池被停止。

- **enqueue()** 函数：将任务封装成一个std::function对象，并将其添加到任务队列中。
- **析构函数**：在析构函数中，我们等待所有线程执行完成后，再停止所有线程。

在主函数中，我们创建了一个ThreadPool对象，并向任务队列中添加了 8 个任务。每个任务会输出一些信息，并在执行完后等待 1 秒钟。由于线程池中有 4 个线程，因此这 8 个任务会被分配到不同的线程中执行。在任务执行完成后，程序会退出

> “通过组合使用 C++11 的 `std::thread`、`std::mutex`、`std::condition_variable` 和任务队列，我们实现了一个基本的跨平台线程池。该线程池通过预先创建线程并在任务队列上等待，避免了频繁创建线程的开销。
>
> 实现中需要特别注意：工作线程必须在**持锁时检查条件**，在**执行任务前释放锁**；析构时**先设置停止标志再通知再 join**，以确保线程安全退出。此外，任务执行期间的异常处理、移动语义的使用以及锁粒度的控制，都是保证线程池健壮性和性能的关键细节。”

## 1. `async` 与 `future`

`std::async`和`std::future`是 C++11 引入的一个功能，允许我们异步**执行一个函数**，并返回一个`std::future`对象，表示异步操作的结果。使用`std::async`可以方便地进行异步编程，避免了手动创建线程和管理线程的麻烦。

### 2. `std::future` 和 `std::shared_future`

- **`std::future`**：独占所有权，**只能调用一次 `get()`**。第二次调用会抛异常或导致未定义行为。
- **`std::shared_future`**：共享所有权，允许多次 `get()`，可拷贝，用于多个消费者等待同一个结果。

### 示例代码

```c++
#include <iostream>
#include <future>

int calculate() {
    // 模拟一个耗时的计算
    std::this_thread::sleep_for(std::chrono::seconds(1));
    return 42;
}

int main() {
    std::future<int> future_result = std::async(std::launch::async, calculate);
    // 在这里可以做其他的事情
    int result = future_result.get(); // 获取异步操作的结果
    std::cout << result << std::endl; // 输出42
    return 0;
}
```

在此例中，使用 `std::async` 函数异步执行了一个耗时的计算，这个计算在另一个线程中执行，不会阻塞主线程。通过 `future_result.get()` 获取异步操作的结果并输出。

### 3. `std::async` 的启动策略（必考）

```c++
std::future<int> f1 = std::async(std::launch::async, func);   // 必须在新线程中执行
std::future<int> f2 = std::async(std::launch::deferred, func); // 延迟到 get() 时才在调用线程执行
std::future<int> f3 = std::async(func); // 由编译器决定
```

- **重要陷阱**：如果使用 `launch::deferred` 且从未调用 `get()`，任务**根本不会执行**。
- **析构阻塞**：`std::future` 的析构函数可能会**阻塞**直到异步任务完成（尤其是 `launch::async` 返回的 `future`）。这源自提案中的“等待”语义，防止任务在后台继续运行而访问已销毁的局部变量。

## 2. `packaged_task`

`std::packaged_task`是一个类模板，用于将一个**可调用对象**（如函数、函数对象或 Lambda 表达式）封装成一个异步操作，并返回一个`std::future`对象，表示异步操作的结果。packaged_task可以方便地将一个函数或可调用对象转换成一个异步操作，供其他线程使用。

### 示例代码

1.定义可调用对象：

```c++
int calculate(int x, int y) {    return x + y;}
```

2.创建 `packaged_task` 对象：

```c++
std::packaged_task<int(int, int)> task(calculate);
std::future<int> future_result = task.get_future();
```

3.在其他线程中执行异步操作：

```c++
std::thread t(std::move(task), 1, 2);t.join();
```

4.获取异步操作的结果：

```c++
int result = future_result.get();std::cout << result << std::endl; // 输出3
```

在此例中，我们成功地将一个函数calculate封装成了一个异步操作，并在其他线程中执行。通过packaged_task和future对象，我们可以方便地实现异步编程，使得代码更加简洁和易于维护。

### 4. `packaged_task` 的深层细节

- **只移型别**：`packaged_task` 不可拷贝，只能移动。因此传入线程时必须 `std::move`。
- **执行后取出 future**：调用 `operator()` 执行任务后，`get_future()` 获取的 `future` 就能得到结果或异常。
- **典型使用**：常用于**任务队列**或自定义线程池。你可以把 `packaged_task` 塞进队列，由工作线程取出执行，实现“提交任务并获得 future”的模式。

## 3. `promise`

`std::promise` 是一个类模板，用于在一个线程中产生一个值，并在另一个线程中获取这个值。`promise` 通常与 `future` 和 `async` 一起使用，用于实现异步编程。

### 示例代码

1.创建 promise 对象：

```c++
std::promise<int> p;
```

2.获取 `future` 对象：

```c++
std::future<int> f = p.get_future();
```

3.在其他线程中设置值：

```c++
std::thread t([&p]() {    p.set_value(42);});t.join();
```

4.在主线程中获取值：

```c++
int result = f.get();std::cout << result << std::endl; // 输出42
```

### 5. `std::promise` 的通信模型与异常传递

在此例中，我们成功地使用promise和future对象实现了跨线程的值传递。通过promise和future对象，我们可以方便地实现异步编程，避免了手动创建线程和管理线程的麻烦。

`promise` 和 `future` 构成一个**一次性的、单向的、线程安全的管道**。

```tex
[设置端] promise.set_value(x)   ────>  [获取端] future.get()
[设置端] promise.set_exception(e) ────>  [获取端] future.get() 抛出 e
```

- **一次性**：一个 `promise` 只能 `set_value` 一次，设置后 `future` 变为“就绪”。
- **异常传递**：如果线程执行出错，不应该直接崩溃，而应该**捕获异常并调用 `p.set_exception(std::current_exception())`**，这样 `future.get()` 会在调用线程重新抛出该异常，从而实现**异常安全**的跨线程传递。
- **必须配对**：如果 `promise` 销毁前既不 `set_value` 也不 `set_exception`，其关联的 `future` 会抛出 `std::future_error`（broken promise）。

## 总结

### 1. 三个工具的核心定位（一句话区分）

- **`std::async`**：**“我只要结果，别让我管线程”** —— 最简单的异步启动，返回一个 `future`，线程管理全自动。
- **`std::packaged_task`**：**“我把任务包好，你拿到线程里跑，结果通过 future 给我”** —— 将可调用对象包装成 `future` 的异步任务，可以手动指定在哪个线程执行。
- **`std::promise`**：**“我承诺将来给你一个值，你拿着 future 等着”** —— 一个线程向另一个线程传递值的管道，适用于更灵活的通信场景。

通过使用 std::async、std::future、std::packaged_task和std::promise，我们可以在 C++ 中实现高效的异步编程。这些工具让线程间的任务调度与值传递更加简洁，避免了复杂的线程管理，提升了代码的可维护性和效率。

### 6. 如何选择？（决策指南）

| 场景                                   | 推荐工具                                           |
| :------------------------------------- | :------------------------------------------------- |
| 我就想异步跑一个函数，懒得管理线程     | `std::async`                                       |
| 我需要自定义线程池，任务执行完通知结果 | `std::packaged_task`（存入任务队列）               |
| 两个线程之间需要灵活传递状态或多次通知 | `std::promise` + `std::future`（再结合条件变量等） |
| 多个线程都需要获取同一个异步结果       | `std::shared_future`（从 `future` 转移构造）       |

| 陷阱                                                         | 后果                                    | 规避方法                                     |
| :----------------------------------------------------------- | :-------------------------------------- | :------------------------------------------- |
| `future.get()` 调用两次                                      | 未定义行为或抛出异常                    | 用 `valid()` 检查，或改为 `shared_future`    |
| `promise` 未设置值或异常就销毁                               | 读取其 `future` 抛出 `future_error`     | 保证在所有路径上设置值或异常，或用 RAII 封装 |
| `packaged_task` 在未执行的情况下销毁                         | `get_future()` 得到的 `future` 抛出异常 | 确保任务被执行                               |
| `async` 返回的 `future` 在最后才调用 `get`，且采用 `launch::deferred` | 任务才在调用线程执行，失去异步意义      | 明确启动策略，或提前调用 `get`               |

> “C++11 提供的 `std::async`、`std::future`、`std::packaged_task` 和 `std::promise` 构成了一套完整的高层次异步编程模型。
>
> `async` 适用于简单的即抛即忘异步执行；
>
> `packaged_task` 可将任何可调用对象封装成返回 `future` 的异步任务，常与线程池结合；`promise` 则提供了更底层的跨线程值通信能力，尤其擅长异常安全传递。
>
> 使用这些工具时，务必注意 `future` 的一次性特性、`promise` 的 broken promise 陷阱，以及 `async` 的启动策略和析构等待行为，这些细节是写出正确、健壮异步代码的关键。”

# 10、C++11 std::atomic

**无锁编程、内存序和 CAS 循环**

## 引言

​	std::atomic是 C++11 标准库中的一个模板类，用于实现多线程环境下的**原子操作**。它提供了一种线程安全的方式来访问和修改共享变量，可以避免多线程环境中的数据竞争问题。

​	std::atomic的使用方式类似于普通的 C++ 变量，但是它的操作是原子性的。也就是说，在多线程环境下，多个线程同时对同一个std::atomic变量进行操作时，不会出现数据竞争问题。

## 1. 原子操作解决什么问题？（一句话核心）

**原子操作保证在多线程环境下，对一个变量的操作“不可分割”**——其他线程看到的该变量状态，要么是操作前，要么是操作后，**绝不存在操作到一半的中间状态**。

- 普通 `int` 的 `++count`：读—改—写三步，线程可能在中间被切走，导致数据竞争。
- `std::atomic<int>` 的 `++count`：CPU 通过硬件指令（如 x86 的 `LOCK` 前缀）锁住缓存行，三步合一，其他核心无法干扰。

## 2. 原子操作 vs 互斥锁（高频面试题）

| 对比维度     | `std::atomic`                      | `std::mutex`                                     |
| :----------- | :--------------------------------- | :----------------------------------------------- |
| **原理**     | CPU 原子指令（无锁）               | 操作系统互斥机制（可能挂起线程）                 |
| **性能**     | 极快（纳秒级），无上下文切换       | 较慢（微秒级），可能进入内核态                   |
| **保护范围** | **单个变量**，只能做有限的原子操作 | **一大段代码**（临界区），可保护任何复杂数据结构 |
| **适用场景** | 计数器、标志位、无锁数据结构       | 复杂共享数据的读写、文件操作                     |
| **阻塞**     | 非阻塞                             | 阻塞                                             |

**必须记住的原则**：对单一基础类型（int、bool、指针）的读写/修改，优先考虑 `atomic`；多个变量需同时修改，或涉及容器操作，必须用 `mutex`。

## 常用的 `std::atomic` 操作

1. **`load()`**：将 `std::atomic` 变量的值加载到当前线程的本地缓存中，并返回这个值。
2. store(val)：将val的值存储到std::atomic变量中，并保证这个操作是原子性的。
3. exchange(val)：将val的值存储到std::atomic变量中，并返回原先的值。
4. compare_exchange_**weak**(expected, val)和compare_exchange_**strong**(expected, val)：
   - 比较std::atomic变量的值和expected的值是否相同，如果相同，则将val的值存储到std::atomic变量中，并返回true；否则，将std::atomic变量的值存储到expected中，并返回false。

### 3. `compare_exchange_weak/strong` —— 无锁编程的基石

这两个函数是实现**无锁数据结构**的核心，理解它们就拿到了现代 C++ 并发编程的钥匙。

**它以原子方式执行以下伪代码：**

```c++
bool compare_exchange_strong(T& expected, T desired) {
    T current = this->load();       // 1. 读出当前值
    if (current == expected) {      // 2. 如果当前值等于我期望的值
        this->store(desired);       // 3. 就设置成新值
        return true;                // 4. 返回成功
    } else {
        expected = current;         // 5. 否则把当前值写入 expected（告诉你“它已经不是你以为的那个值了”）
        return false;               // 6. 返回失败
    }
}
// 以上三步(1-2-3)是原子执行的，中间不会有其他线程插入修改
```

**典型的 CAS（Compare-And-Swap）循环用法**：

```c++
std::atomic<int> value = 0;

void safe_increment() {
    int expected = value.load();
    // 循环直到成功
    while (!value.compare_exchange_weak(expected, expected + 1)) {
        // 如果失败，expected 已被更新为当前值
        // 循环会再次基于新的 expected 重试
    }
}
```

**`weak` vs `strong` 的区别**：

- `compare_exchange_strong`：除非当前值不等于 `expected`，否则**一定**成功。实现简单，失败一定是值不匹配。
- `compare_exchange_weak`：即使当前值等于 `expected`，它**也可能“伪失败”**（Spurious Failure），直接返回 `false`。这源于 ARM 等平台用 LL/SC 指令实现 CAS 的硬件特性。
- **使用原则**：如果你在**循环**里反复尝试（就像上面那样），**优先用 `weak`**，因为硬件效率更高；如果只需要**只调一次**并根据成败做出不同业务逻辑，用 `strong`。

### 4. `memory_order`（内存序）—— 决定原子操作的同步边界

`std::atomic` 的每个操作都可以传入一个 `std::memory_order` 参数，它决定了：

- 该操作前后的普通内存操作**能否越界重排**。
- 该操作在多线程间的**可见性同步**强度。

| 内存序                 | 保证                                   | 开销 | 典型场景                     |
| :--------------------- | :------------------------------------- | :--- | :--------------------------- |
| `memory_order_seq_cst` | **默认**，全局顺序一致性，双向内存屏障 | 最高 | 不追求极致性能时的安全选择   |
| `memory_order_acquire` | 读操作的**读屏障**，后面读写不可前移   | 较低 | 锁的获取端、消费者读数据     |
| `memory_order_release` | 写操作的**写屏障**，前面读写不可后移   | 较低 | 锁的释放端、生产者写数据     |
| `memory_order_relaxed` | 只保证原子性，**不保证顺序和可见性**   | 最低 | 纯计数器（允许短暂读取旧值） |

```c++
// 用 relaxed 做高性能引用计数（不在乎与其他操作的顺序）
cnt.fetch_add(1, std::memory_order_relaxed);

// 生产者-消费者用标志位时，必须用 acquire-release 配对
// 生产者
data = 42;
ready.store(true, std::memory_order_release); // 保证 data=42 在 ready 之前写回内存
// 消费者
if (ready.load(std::memory_order_acquire)) {  // 保证读 data 在 ready 之后
    use(data); // 此刻一定能看到 data=42
}
```

#### 5. 常见陷阱

| 陷阱                                   | 正确做法                                                     |
| :------------------------------------- | :----------------------------------------------------------- |
| `count = count + 1;`                   | **不是原子的**。必须用 `count++` 或 `count.fetch_add(1)`     |
| `std::atomic<bool> flag; flag = true;` | `operator=` 是原子的，没问题。但要清楚它等价于 `store(true)` |
| 忘掉 `is_lock_free()`                  | 某些复合类型（如 256 字节的大结构体）的 `atomic` 内部可能退化为用互斥锁实现。用 `is_lock_free()` 检查 |
| 过度使用 `seq_cst`                     | 非必须的场景（如简单打点计数器）用 `relaxed` 能大幅提升性能  |

## 示例代码

```c++
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<int> count = 0;

void increment() {
    for (int i = 0; i < 1000000; ++i) {
        count++;
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join();
    t2.join();
    std::cout << count << std::endl;
    return 0;
}
```

​	在这个示例中，我们定义了一个 std::atomic<int>类型的变量count，并将其初始化为 0。然后，我们启动两个线程分别执行increment函数，这个函数的作用是将count变量的值加一，执行一百万次。最后，我们在主线程中输出count 变量的值。

​	由于count变量是一个std::atomic类型的变量，因此对它进行操作是原子性的，不会出现数据竞争问题。在这个示例中，最终输出的count变量的值应该是 2000000。

## 总结

> “`std::atomic` 是 C++11 提供的无锁编程基础，它利用 CPU 原子指令让单一变量的操作变为不可分割，从而在性能敏感的场景（如计数器、标志位、无锁队列）中取代互斥锁。使用 `std::atomic` 时，必须注意：`++` 和 `fetch_add` 才是原子的，分步写入不是；`compare_exchange_weak/strong` 是实现 CAS 循环的核心，`weak` 版本应放在循环里；而 `memory_order` 内存序决定了操作的同步强度，默认的 `seq_cst` 安全但昂贵，合理使用 `relaxed` 和 `acquire-release` 可以显著提高并发性能。”
